EXECUTION ORDER
- The adapter invokes restore(client, original_service, bounded_health_callback)
  once after identity, state, operations, digest and service-identity preflight.
- It prepares a deep-copied SourceConfiguration and fresh key in memory; it changes
  only ImageIdentifier and the eight approved runtime names (seven settings plus
  AUTH_SECRET_KEY), removing conflicting secret references for those names.
- It submits ResumeService once, then polls that exact operation ID to SUCCEEDED
  and confirms RUNNING. It immediately submits one UpdateService containing the
  image and runtime changes together. No StartDeployment call.
- ImageIdentifier uses the verified repository@sha256:digest, not mutable :latest.
- UpdateService omits networking, health checks, instance settings, scaling,
  encryption, observability and unrelated service fields, preserving them.
- Poll the exact update operation ID to SUCCEEDED, then verify RUNNING, exact
  desired source configuration and unchanged unrelated settings in memory.
- health callback: GET https://api.mrrc.online/health with TLS verification,
  redirects disabled, bounded response size, 5-second request timeout, and a
  total deadline of 60 seconds enforced by a main-thread alarm. It accepts at
  most 4096 response bytes, ignores proxy environment, and requires HTTP 200
  and JSON {"status":"healthy"}.
  Return True only on success; never print raw body or HTTP exception details.
  Do not query resident data or test login/passwords as part of this operation.
- Print only operation IDs, digest, and fixed pass/fail labels. /health alone does
  not establish database authorization or full application functionality.

FAILURE AND TIMEOUT
- Any exception after a resume attempt (including an ambiguous network timeout
  or KeyboardInterrupt) enters containment. Never blindly retry the update.
- Pause immediately if RUNNING; if an operation is still in progress, wait until
  a pause is permitted. Confirm the pause operation succeeded AND status PAUSED.
- Default operation deadline: 15 minutes each. Separate containment deadline:
  15 minutes. These are maximum waits, not promised restoration times.
- If containment is unconfirmed, stop automation and escalate to the operator
  for status/operation inspection and an authorized pause as soon as allowed.
  Do not claim the service is stopped. A killed process cannot run containment.
- Never restore the vulnerable image, restore the database snapshot, rotate the
  database password, resume the frontend, or retry restoration automatically.
- Failed updates can roll back to the old source. Pause is containment, not a
  guarantee that the old source stopped serving before the pause completes.
