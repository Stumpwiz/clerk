# Local Authentication Architecture

Status: production

Version: 2.0.0

The application uses local database-backed authentication. Authentication is intentionally simple: every authenticated active user is trusted to use the administrative application, and unauthenticated users have no application access. There are no roles, permission levels, external account provisioning workflows, or secondary login identifiers.

## Architecture

Local authentication is implemented by the FastAPI backend and the local `users` table.

- Users authenticate with email and password.
- Email is the only login identifier.
- Passwords are stored only as hashes generated by the backend password utility.
- The backend issues signed HTTP-only session cookies.
- The frontend sends API requests with credentials so the browser includes the session cookie.
- Backend routers enforce authentication before protected application data is returned.
- Inactive users cannot log in.

The local user model contains:

- `id`
- `email`
- `password_hash`
- `display_name`
- `avatar_path`
- `is_active`
- `last_login_at`
- `created_at`
- `updated_at`

## Login And Logout Flow

1. The user opens `/local-login`.
2. The frontend posts email and password to `POST /api/auth/login`.
3. The backend normalizes the email, verifies the password hash, rejects inactive users, updates `last_login_at`, and sets the signed HTTP-only session cookie.
4. The frontend routes the user into the dashboard.
5. Protected frontend views call `GET /api/auth/me` through `frontend/lib/auth.ts` to load the current user.
6. Logout posts to `POST /api/auth/logout`, which clears the session cookie and returns the user to the local login page.

Session cookies are configured by backend environment variables:

- `AUTH_SECRET_KEY`
- `SESSION_COOKIE_NAME`
- `SESSION_COOKIE_SECURE`
- `SESSION_COOKIE_SAMESITE`
- `SESSION_TTL_SECONDS`

Production must use a strong `AUTH_SECRET_KEY` and HTTPS-compatible cookie settings.

## User Lifecycle

Local user administration is available from the Users page:

- List users.
- Add a user with email, display name, password, and active flag.
- Edit display name and active flag.
- Activate or deactivate a user through the active flag.
- Reset another user's password as an administrator.

Operational rules:

- Email addresses are immutable login identifiers.
- Duplicate email addresses are rejected case-insensitively.
- Display names are trimmed and cannot be blank.
- Password hashes are never returned to the frontend.
- Deactivated users are retained in the database but cannot log in.

## Password Management

Self-service password changes are available from the Profile page.

The current user must provide:

- Current password.
- New password.
- Confirmation.

The backend verifies the current password, requires the new password to be at least 8 characters, requires the new password to differ from the current password, hashes the new password, and preserves the current session.

Administrator password reset is available from the Users page.

An authenticated administrator can set a new password for another local user without knowing the current password. The reset endpoint requires only that the target user exists and the new password is at least 8 characters.

## First User Bootstrap

A fresh environment needs one initial active local user before anyone can sign in. Create that user from the backend environment after `DATABASE_URL` is configured and migrations have run:

```bash
cd backend
python scripts/create_local_user.py
```

The script prompts for email, display name, password, and password confirmation. It lowercases the email, rejects duplicates, hashes the password, and creates an active user.

For containerized environments, run the same script inside the backend container or one-off backend task with the production `DATABASE_URL` and `AUTH_SECRET_KEY` available.

## Environment Variables

Backend required:

- `DATABASE_URL`: PostgreSQL connection string.
- `AUTH_SECRET_KEY`: high-entropy secret used to sign session cookies.
- `CORS_ORIGINS`: comma-separated list of frontend origins allowed to call the API with credentials.

Backend recommended:

- `SESSION_COOKIE_NAME`: defaults to `clerk_session` for continuity with existing deployments.
- `SESSION_COOKIE_SECURE`: `true` in HTTPS production.
- `SESSION_COOKIE_SAMESITE`: usually `lax` for same-site deployments; review if frontend and backend are cross-site.
- `SESSION_TTL_SECONDS`: session lifetime in seconds.
- `DEBUG`: `false` in production.

Frontend required:

- `NEXT_PUBLIC_API_URL`: public backend API base URL used by the browser.

No third-party identity-provider environment variables are required.

## Deployment Requirements

Before deployment:

1. Configure the backend with `DATABASE_URL`, `AUTH_SECRET_KEY`, `CORS_ORIGINS`, and production cookie settings.
2. Configure the frontend with `NEXT_PUBLIC_API_URL`.
3. Run Alembic migrations against the target PostgreSQL database.
4. Create the initial local administrator if the database has no active users.
5. Confirm the frontend origin is included in `CORS_ORIGINS`.
6. Confirm the backend allows credentials and the browser receives the HTTP-only session cookie.

After deployment:

1. Sign in with the local administrator.
2. Confirm dashboard access.
3. Confirm logout clears access.
4. Confirm inactive users cannot log in.
5. Confirm Add User, Edit User, Change Password, and Reset Password work.

## Administrator Responsibilities

Administrators are responsible for:

- Creating and maintaining local user accounts.
- Deactivating users who no longer need access.
- Resetting passwords when users cannot complete self-service change.
- Protecting production environment variables, especially `AUTH_SECRET_KEY` and `DATABASE_URL`.
- Understanding that rotating `AUTH_SECRET_KEY` invalidates existing signed sessions.

## Security Notes

- The application does not support public signup.
- Password policy is intentionally simple: minimum 8 characters.
- Signed cookies support normal expiration but not targeted per-device revocation.
- Add database-backed sessions later only if targeted session revocation or detailed session audit becomes a real operational requirement.
- Use HTTPS in production and set `SESSION_COOKIE_SECURE=true`.

## Verification Checklist

Use this checklist after local setup or deployment:

- Fresh environment can create the first local administrator.
- Local administrator can log in.
- Protected pages reject unauthenticated access.
- Backend protected endpoints reject unauthenticated requests.
- Active users can log in.
- Inactive users cannot log in.
- Add User creates a hash-only password record.
- Duplicate email creation is rejected.
- Edit User updates display name and active flag only.
- Change Password accepts the correct current password and rejects the old password afterward.
- Administrator Reset Password allows the target user to log in with the new password and rejects the old password afterward.
- Logout clears the session.
